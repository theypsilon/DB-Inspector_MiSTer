# Testing

The tests form a pyramid, and each layer covers what the one below cannot reach:

- Unit tests (`npm run test:unit`, about a second): the plain modules, and every user flow at the model level.
- Component tests (`npm run test:component`, about 20 seconds): what the components show, which handler each control calls, and the page wired to the model, in jsdom.
- Journeys (`npm run test:e2e`, about 20 seconds): a few long flows in a real browser, against the production build, for layout, virtualization, scrolling, highlights, drag-and-drop, downloads and history.

Every check goes in the lowest layer that can capture it. The journeys are the slowest layer by far, so they hold only what the others cannot (see End-To-End Journeys): a check a lower layer can make moves there, with a test that fails without it, and the journey keeps only the actions that bring the page to what it checks. A change to a flow belongs in its unit flow test; a change to what a component shows or calls, in its component test; and a journey step checks only what needs a real browser. The legacy end-to-end suite (`tests/*.spec.js`) is skipped; see Legacy End-To-End Suite.

Every suite's command, and the build, lint and type checks, are in [AGENTS.md](../AGENTS.md#commands). Lint, typecheck, the unit and component tests and the build are independent, and run at the same time in about 20 seconds, as long as the component tests take; the journeys come after, with their own build.

## Unit Test

- Command: `npm run test:unit` (Node's test runner over `tests/unit/**/*.test.js`)
- `tests/unit/flows/` specs every user flow at the model level: one file per legacy end-to-end spec (same name) and one unit test per legacy end-to-end test, under the same title. Each one runs its scenario against the app model and the plain modules, and checks what the page would show: headings, rows, prompts, FILTER values, links, picker selections, and the layout math behind scrolling and anchors. New flows get their unit flow tests here too.
- The harness settles the app after each action (`settle` in `tests/unit/support/app.js`): it runs the timers due on the fake clock, waits for the work the fake browser tracks (responses and their bodies, file reads, digests: `tests/unit/support/browser.js`), and returns once nothing has changed for three tasks in a row with nothing in progress. One task is enough today; the others are a margin. It used to wait twelve `setTimeout(0)`s in a row instead, which Node rounds up to a millisecond each: 94% of the flow tests' time, and the unit suite took 2.1 seconds rather than about one.
  - Waiting for tracked work rather than for time is what keeps a settled test from reading the page early. When the app starts waiting on anything the fake browser does not track (another browser API that settles later, a real timer rather than `window.setTimeout`), track it there, or `settle` can return before it is done, and a test that checks that something does not happen passes for the wrong reason.
  - When the change came in, every `settle` of every unit test was followed by the old one, which found nothing more to wait for; with the tracking off, the old one found 17 tests settled too early, and 7 tests fail.
- What the model cannot show is left to the component tests (JSX copy and markup, which handler answers which question, Escape in nested dialogs, the page's wiring) and to the journeys (CSS, layout, real scrolling and measurement). The real-database scroll flow tests replay the virtual tree's measurement and anchoring rules over a synthetic database shaped like Distribution_MiSTer.

## End-To-End Journeys

- What only a real browser can show, and so what the journeys are for:
  - layout and CSS: sizes, positions, wrapping, what fits a phone's width, the breakpoints, the themes' colors;
  - real scrolling, and the virtual tree's and the explorer's measured rows: what renders near view, rows touching, reaching the last rows, anchors and find-in-page jumps landing in view;
  - what is painted: find-in-page highlights (the CSS Custom Highlight API) and `content-visibility`;
  - animations and transitions, and what moves under the pointer;
  - the browser's own handling of files, dropped folders, downloads and new tabs;
  - what a real page load does: the theme before the first paint, a reload that scrolls back to an anchor.
- Everything else is checked lower: the model's flows (links, FILTER, history, questions, selections, errors) in unit flow tests, and what the page shows and which handler a control calls in component tests. A journey step drives the page to what it checks with whatever actions that takes, but its checks are of the kinds above.
- Command: `npm run test:e2e` (Playwright; it runs `tests/journeys/`, while the legacy specs are skipped)
- Config: `playwright.config.js`
  - Tests run fully parallel on 4 workers; keep them independent of each other.
  - The journeys run the production build, as GitHub Pages serves it: each run builds the app into `node_modules/.journeys-build` and serves it with `vite preview` on `[::1]:4173`. The build's output goes to a log beside it, shown only when the build fails (its CSS optimizer warns about every `::highlight` rule). A server already on the port is never reused, so the journeys always test the code as it is; with the dev server, React's development build and its StrictMode made the same pages slower. Under WSL2 mirrored networking, Playwright's check of a closed `127.0.0.1` port hangs for about two minutes before every run, hence the IPv6 loopback.
  - A run lasts as long as its longest test, so a long journey is split into tests that each start on a fresh page and run on separate workers: the large-tree and shared-link journeys are three tests each, and the catalog's two. Four workers: at eight, the CPU they share slowed the large-tree test's scroll to the end of the archives (see Known Gaps) past its 10-second wait.
  - The opt-in real-database journey (`REAL_SCROLL_URL`) measures scroll timing, so the config runs it on a single worker.
  - Playwright ignores `tests/unit/` and `tests/component/`, which other runners own.
- Each journey walks a user flow in `test.step`s, in one test or a few that each start on a fresh page. Add a step to the closest journey rather than a new test, and only for what needs a real browser; a test's later steps rely on its earlier ones. When a test grows long, split it where a step starts on a fresh page, and give the new test what the steps before it left (the database, the scroll position, the page clock).
- Journeys must not be flaky, so they never assume how long the page takes. A check waits for what the page shows, never for a fixed time, and each step leaves no work running for the next one:
  - Scroll with `scrollUntilSteady` (large-tree), which scrolls again until the position holds for ten frames. Rows measured during a scroll apply their heights 120 ms after it stops, which can move what was just scrolled to.
  - A find-in-page or anchor jump scrolls its row into place again 300–500 ms after it lands, and section anchors scroll smoothly: wait for the page to stop scrolling (`untilScrollStops`) or start the next step on a fresh page (`about:blank`, then the app), before anything that depends on positions or hovering. Row link icons show only under the pointer.
  - For timed behavior, pause the page clock (`page.clock.pauseAt`) and move it with `runFor`, as the row flash step does. `runFor` also runs the timers those timers start; `fastForward` does not, so their work would spill into the next step.
  - A negative check (no ghost, no question) comes after something that proves the page has caught up: a positive check, or two drawn frames (`afterTwoFrames`).
  - An emptied FILTER reaches the address 600 ms later, and from there decides the FILTER of the next database opened, so a step that relies on an empty FILTER starts on a fresh page.
  - FILTER and row anchors reach the link after the page writes them (FILTER 600 ms after typing): wait for the link itself before reloading.
  - Going to the same page with only another `#` does not load it again; it opens the link in the page, as the address bar does. A step that needs a fresh page goes through `about:blank` first.
  - Elements with `content-visibility: auto` (the filter terms) are in the page before the browser has told which are on screen, which it does by the next frame; until then `checkVisibility({ contentVisibilityAuto: true })` calls them all skipped. Wait for one on screen to be laid out before checking that one off screen is not.

## Legacy End-To-End Suite

- `tests/*.spec.js` hold the 60 end-to-end tests the project used to run. They are skipped: each file starts with `test.skip(!process.env.LEGACY_E2E, …)`.
- Run them on demand with `LEGACY_E2E=1 npx playwright test tests/*.spec.js` (the real-database ones also need `REAL_SCROLL_URL`).
- Their coverage moved to the layers above: each test has a unit flow test under the same title, and what it checked in the browser is in the component tests or the journeys. Mutation testing (one-line bugs across the model, the plain modules and the components) confirmed that every bug the legacy suite catches is caught by the new layers.
- Do not add to them; extend the layers above instead.

## Known Gaps

Nothing tests these yet. When you change one of them, add its tests:

- INI parsing edge cases, beyond the `[mister]` section and entry filters (`ini-source.test.js`, `database-parsing.test.js`).
- The drop area's drag states: its look while files are dragged over it (`isDragActive`) and right after a drop (`isDropPulseActive`). The uploads journey drops files and folders, but checks only what they open.
- The remote URL aliases (`REMOTE_SOURCE_URL_ALIASES` in `database.js`): no test opens an aliased URL.
- An uploaded INI list adding all its entries to the catalog.
- Catalog text staying selectable, so it can be copied.
- The tree section updating the layout it shows when rows are measured, rather than building it again (`useVirtualTree.js`, `docs/design.md`, 6): the unit tests cover the update, and no test fails if the section builds the layout instead, which only makes scrolling a large list slow again. It was measured in Chrome and Firefox over the 226 databases of the catalog combined.
- One scroll to the end of the Archives list with Files and folders closed: `scrollUntilSteady` scrolls again until the list holds still where it should, so a list that does not get there at the first scroll passes. Since d51dcb5 it does not: pressing End there leaves the page thousands of pixels short of the bottom, the last archive entry not rendered (305px short, with it on screen, at 6170c4b), and the large-tree test's first scroll there takes 67 frames to settle.
- Fitting tags whose names go beyond ASCII, or before the web font arrives: the journeys fit ASCII names only, in the font as loaded. The fallback monospace font has the same character width in Chrome on Linux, so a late font changed nothing there; the sample row measures again when its sample tag changes width.
